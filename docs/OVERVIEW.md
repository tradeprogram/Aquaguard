# AquaGuard AI — 프로젝트 소개

> 이 문서는 코드를 처음 보는 분을 위한 안내서입니다. 무엇을 만들었고, 어떤 데이터를 쓰며,
> 어디까지가 실제로 동작하고 어디부터가 아직 목업인지를 한 번에 알 수 있게 정리했습니다.
>
> 더 깊은 설계 근거는 [ARCHITECTURE.md](../ARCHITECTURE.md), 모듈 간 입출력 계약 원본은
> [`contracts/`](../contracts/), 개발 인수인계 기록은 [HANDOFF.md](../HANDOFF.md)에 있습니다.

## 1. 한 문장 요약

**아쿠아가드는 새로운 산사태 위험지도가 아닙니다.** 산불·강우·지형·하천이라는 이미 존재하는
신호들을 하나의 재해연쇄로 연결해, 위험도가 임계치를 넘은 순간 *"어떤 도로가 끊기고, 어떤
마을이 고립되며, 누구를 어느 대피소로 보내야 하는지"* 를 하나의 의사결정 패키지로 자동
생성하고, 그 의사결정이 실제 재난에서 몇 분 빨라질 수 있었는지를 검증하는 시스템입니다.

## 2. 왜 만들었는가

### 2.1 문제의 배경

2025년 여름, 한반도는 한 시즌 안에 복합재해를 겪었습니다. 7월 16~20일 집중호우로 전국
**37명 사망, 12,921명 대피, 피해액 1조 848억원**을 기록했습니다.

가장 심각했던 곳은 경남 산청군입니다. 7월 19일 하루에 **산사태 266건, 13명 사망·1명 실종**.
그런데 이 사건에서 실패한 것은 예측이 아니었습니다.

- 산림청은 이미 **7월 17일**에 대피를 권고한 상태였습니다.
- 산사태 경보가 실제로 격상된 시각은 **7월 19일 12시 37분**이었습니다.

**위험 신호는 이미 있었고, 그 신호가 관(官)의 판단·전파 단계에서 여러 시간 새어나갔습니다.**

여기에 우연이 아닌 연결고리가 하나 더 있습니다. 같은 산청군은 이 산사태 **4개월 전(2025년
3월)**, 경남·경북 11개 지역 48,238ha를 태운 대형 산불의 피해지였습니다. 산불로 훼손된 사면은
나무 뿌리의 토양 결속력과 토양의 빗물 흡수력을 동시에 잃어, 화재 2년 후까지도 토양유출량이
일반 산림 대비 3~4배 높게 유지됩니다.

### 2.2 그래서 푸는 문제 두 가지

1. **재해연쇄를 하나로 모델링하는 시스템이 없다.** 산불위험·산사태·홍수 예측은 각각
   독립적으로 존재하지만, "산불이 할퀸 사면 + 첫 폭우 → 산사태 → 하류 하천범람 → 도로 단절 →
   마을 고립"이라는 인과 사슬을 끝까지 추적하는 시스템은 없습니다.
2. **정확한 예측이 있어도 판단·전파에서 시간이 샌다.** 산청이 정확히 그 사례입니다.

그래서 이 프로젝트의 목표는 *"더 정확한 예측 모델"* 이 아니라 **"이미 존재하는 신호와 실제
대피 사이에서 새는 시간을 자동화로 되찾는 것"** 입니다.

## 3. 시스템 아키텍처

### 3.1 전체 구조

```
                    ┌──────────── 관측·정적 데이터 ────────────┐
                    │ 지형(DEM) · dNBR · 강수 · 하천수위 · InSAR │
                    └───────────────────┬──────────────────────┘
                                        ▼
        ┌───────────────────────────────────────────────────┐
        │  Module A  산사태 예측    (FoS 기반, 트랙①)        │
        │  Module B  하천범람 예측  (SFINCS/ANUGA, 트랙①)    │
        │  Module C  도로·지하차도  (규칙기반, 모델 아님)     │
        └───────────────────┬───────────────────────────────┘
                            ▼  임계치 초과 시에만
        ┌───────────────────────────────────────────────────┐
        │            Module O — 골든타임 오케스트레이터       │
        │   상태머신 7단계: 관측→예측→1차권고→시민역검증      │
        │                  →경보격상→주민전파→개별대피        │
        └───┬──────────┬──────────┬──────────┬──────────────┘
            ▼          ▼          ▼          ▼
      Module D    Module E    Module G    Module H
      노출자산     대피경로     피해비용     시민 역검증
      오버레이     ·고립탐지    추정         (신뢰도 보정)
            └──────────┴──────────┴──────────┘
                            ▼
              경보 패키지(alert_package) 생성·전파
                            ▼
        ┌───────────────────────────────────────────────────┐
        │  UI — 3D 지도 대시보드 (시민 모드 / 관공서 모드)    │
        │  + LLM 챗봇 해설층 + Provenance 배지               │
        └───────────────────────────────────────────────────┘

        Module V — 검증 엔진: A/B의 예측 폴리곤과 사후 관측(SAR)을
                   자동 대조해 IoU·F1·Recall·lead time 산출
```

### 3.2 모듈별 역할과 현재 상태

| 모듈 | 역할 | 산출 | 상태 (줄 수는 테스트 제외 구현 코드) |
|---|---|---|---|
| **A** 산사태 | Infinite Slope 기반 안전율(FoS, TRIGRS 원리) → 확률·`hours_to_critical` | `landslide_prob`, `risk_polygon_5179` | 계약 확정, 실모델 개발 중 |
| **B** 하천범람 | SFINCS(1순위)/ANUGA 통합 — 자체 solver 미작성 | `flood_prob`, `inundation_extent_5179` | 계약 확정, 실모델 개발 중 |
| **C** 도로·지하차도 | **규칙기반**(예측 모델 아님). 기상청 호우특보 기준 임계값 적용 | `alert_level` (정상/주의/경계/위험) | **구현 완료** (598줄) |
| **D** 노출자산 | 위험 폴리곤 ∩ 건축물·농경지 공간연산 | `exposed_buildings`, `exposed_farmland_ha` | **구현 완료** (849줄) |
| **E** 대피경로·고립 | 네이버 Directions 실도로 경로 + 도로망 그래프 고립 탐지 | `route_5179`, `isolated_areas` | **구현 완료** (524줄) |
| **G** 피해비용 | 국토부·농식품부 고시 단가 기반 산정 | `estimated_cost_krw`, `cost_range_krw` | **구현 완료** (459줄) |
| **H** 시민 역검증 | 시민 신고를 shrinkage 집계로 신뢰도 보정 | `verification_status`, `confidence_adjustment` | **구현 완료** (703줄) |
| **O** 오케스트레이터 | 위 전부를 순서대로 호출해 경보 패키지 생성 | `alert_package`, `golden_time_saved_min` | **구현 완료** (728줄) |
| **V** 검증 엔진 | 예측 vs 사후 관측 자동 대조 | IoU/F1/Recall/lead_time | 계약 확정, 구현 예정 |

### 3.3 모듈 간 계약 (contracts/)

모든 모듈은 **JSON Schema로 입출력이 고정**되어 있고([`contracts/`](../contracts/)),
공통 응답 봉투를 씁니다:

```jsonc
{
  "status": "ok" | "degraded" | "error",
  "fallback_tier": 1 | 2 | 3,     // 몇 순위 데이터로 계산했는가
  "data": { /* 모듈별 계약 필드 */ },
  "warnings": ["사람이 읽을 수 있는 경고"]
}
```

이 구조 덕분에 **한 모듈이 실패해도 파이프라인 전체가 멈추지 않습니다.** 실패는 예외가 아니라
`status: degraded` + 경고로 표현되고, 상위 모듈이 그 tier를 이어받습니다.

각 계약 예시 파일(`module_X.example.json`)은 **자기 input으로 자기 output을 실제로 재현할 수
있는지** 테스트로 고정되어 있습니다.

### 4.3 화재흉터 증폭계수의 근거

```
f(dNBR, Δt) = 1 + (A_max(dNBR_class) − 1) × decay(Δt)
```

| 근거 | 수치 | 출처 |
|---|---|---|
| 국내 실측 | 화재 2년 후에도 토양유출량 일반 산림 대비 3~4배 | 산림청(2000 동해안 산불) |
| 침투속도 | 화재 6개월 후 강우침투속도 2배 이상 | 국제 문헌(KIGAM 인용) |
| 확률증분 | 강우유발 산사태확률 +20~30% | 그리스 사례(KIGAM 인용) |

> **주의**: `A_max` 등급값(low 1.2 / moderate 2.0 / high 3.5~4.0)은 **문헌값을 가져다 쓴
> 가정치**이며, 아직 한국 데이터로 사후검증된 계수가 아닙니다. 2025년 3월 산불 11개 지역의
> dNBR을 자체 산출해 보정하는 것이 다음 과제입니다.

### 4.4 데이터 범위 (AOI)

| AOI | 범위 | 건물 | 농경지 |
|---|---|---|---|
| **산청** (메인) | 경보지점 반경 12km (452km²) | 18,032동 | 23,288필지 (2,587ha) |
| **서울** (확장성) | 강남구 + 서초구 (84.8km²) | 41,814동 | — |

산청 AOI를 행정경계가 아니라 **경보지점 반경**으로 자른 이유가 있습니다. 행정경계로 자르면
경계 근처에서 위험영역이 밖으로 새어 노출자산이 조용히 누락됩니다 — 생비량면(44km²)으로
잘랐을 때 6km 위험영역의 18%가, 산청군 전체(790km²)로 넓혀도 12%가 밖이었습니다(데모 좌표가
군 동쪽 경계에서 5.4km 지점이기 때문입니다). 반경 12km는 그 누락을 0으로 만듭니다.

## 5. 신뢰성 설계 — 이 프로젝트가 가장 공들인 부분

재난 시스템에서 가장 위험한 것은 모델의 낮은 정확도가 아니라, **결과를 실제보다 확실한 것처럼
포장하는 것**입니다. 그래서 다음 장치들을 시스템 전체에 강제했습니다.

### 5.1 Provenance 배지 — 모든 숫자에 출처를 붙인다

화면의 모든 값에는 다음 중 하나가 반드시 붙습니다.

| 배지 | 의미 | 예 |
|---|---|---|
| `OBSERVED` | 실측값 | 시민 신고, 실측 강수·수위 |
| `FORECAST` | 외부 기관 예보 | LDAPS 강수 예보 |
| `MODEL` | 자체 모델 계산값 | Module A/B 확률, 대피 경로 |
| `RULE` | **규칙 기반 판정** (모델 아님) | Module C 지하차도 경보 |
| `ASSUMPTION` | 사용자 가정값 | What-if 시뮬레이터 값 |

`RULE`은 4단계 체계에 나중에 추가한 다섯 번째입니다. Module C는 학습·추론한 값이 아니라
관측 강우에 고시 임계값을 적용한 결정론적 분류라, `MODEL` 배지를 달면 그 자체가 부정확한
표기가 되기 때문입니다.

### 5.2 가정은 숨기지 않고 별도로 표시한다

배지 하나로는 정직할 수 없는 값이 있습니다. **"노출 건물 1,945동"은 공간연산 결과**지만,
**"피해액 45억"은 그 위에 필지 단위 주용도 조인과 "1동=1세대" 가정이 얹힌 값**입니다.

- 전부 `MODEL`로 표기하면 → 피해액에 얽힌 가정이 화면에서 사라집니다.
- 가정이 하나라도 있으면 `ASSUMPTION`으로 내리면 → 실측 건물 수까지 가정값으로 읽힙니다.

그래서 **배지는 "어떻게 산출됐는가", 별도 칩은 "무슨 가정이 얹혔는가"** 로 채널을 나눴습니다.
피해액은 `MODEL · 가정 2건`으로 표시되고, 펼치면 각 모듈의 `explain()`이 실제로 반환한 문구가
그대로 나옵니다. UI가 문구를 지어내면 모듈의 실제 가정과 어긋날 수 있기 때문입니다.

### 5.3 폴백 계층 — 최상급 데이터가 없어도 멈추지 않는다

| 모듈 | 1순위 | 2순위 | 3순위 |
|---|---|---|---|
| A 산사태 | InSAR+실측강수 | 지형+실측강수 | LDAPS 예보(신뢰구간 확대) |
| B 하천범람 | 실측강수+수위+SAR | 실측강수+SAR | 실측강수만 |
| C 도로 | 입력 4개 정상 | 배수등급·지정위험 결측 → 보수적 기본값 | 강우 결측 → 최소 등급 |
| D 노출자산 | 폴리곤·건물·농경지 정상 | 점 버퍼 대체, 무효 지오메트리 복구 | 위험 지오메트리 없음 → 0건 |
| H 시민 역검증 | 응답 다수 | 응답 소수(낮은 가중치) | 응답 0건(보정값 0) |

**"확인 불가"와 "0"을 구분합니다.** 예를 들어 농경지 레이어를 못 읽으면 `exposed_farmland_ha`는
0으로 계산되지만, 시스템은 *"이는 '없음'이 아니라 '확인 불가'"* 라는 경고를 함께 냅니다.

### 5.4 자동화의 범위를 의도적으로 제한했다

개발 초기에는 담당자가 일정 시간 응답하지 않으면 시스템이 자동으로 경보를 승인하는 로직이
있었습니다. **이를 완전히 삭제했습니다.**

생명안전과 직결된 공공 의사결정에서 "무응답 시 자동승인"은 책임 소재를 불분명하게 만드는
구조적 결함이기 때문입니다. 현재는:

```
15분 무응답 → 긴급 재알림 → 상위 담당자 escalation → 승인 전까지 '권고' 상태 유지
```

**시스템은 어떤 경우에도 공식 대피명령을 독자 발령하지 않습니다.** 최종 판단은 담당자(관공서
모드) 또는 사용자 본인(시민 모드)의 몫입니다. 이 원칙은 코드 레벨 테스트로 고정되어
있습니다(`test_escalation_after_timeout_does_not_auto_approve`).

### 5.5 검증을 별도 모듈로 분리했다

Module V는 사후 관측 데이터(Sentinel-1 SAR, 실측 인벤토리)와 사전 예측 폴리곤을 자동 대조해
IoU·Precision·Recall·F1·lead time을 계산합니다. 핵심 설계 규칙은 **data leakage 금지** —
사건 이후에 취득한 데이터를 예측 입력에 절대 섞지 않습니다.

- **LLM 챗봇 해설층** — Module O의 경보 데이터만 인용하도록 시스템 프롬프트로 제약,

## 8. 확장성

이 시스템은 산청과 강남·서초라는 두 지역, 산사태·하천범람이라는 두 재해에 묶여 있지 않습니다.

- **지역 확장**: 데이터 스택과 모듈 계약이 지역 무관하게 설계되어 있어, 다른 지자체의
  브이월드 데이터와 강수·지형 데이터만 연결하면 같은 파이프라인이 그대로 돕니다. 강남·서초
  AOI가 그 증거입니다 — 산청과 완전히 다른 성격(도시 vs 산간)인데 같은 코드로 돕니다.
- **재해 유형 확장**: Module C처럼 모델이 아닌 규칙기반 경보를 파이프라인에 낮은 비용으로
  추가할 수 있는 구조라, 폭염·가뭄 등 다른 재난으로 같은 골든타임 회복 프레임워크를 넓힐 수
  있습니다.
- **모듈 교체**: 모든 모듈이 `run(input) -> envelope` 하나의 진입점만 노출하므로, Module B를
  SFINCS에서 다른 수리모형으로 바꿔도 나머지 코드는 수정할 필요가 없습니다.
